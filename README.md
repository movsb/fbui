# trimui

## 从 GM 远程启动 ROM

GM 二进制优先从 SD 卡的 `Blobs/<sha256 前两位>/<完整 sha256>` 读取，可将 GM blobs 目录的内容原样复制到 `sdcard/Blobs/`，保留子目录和 gzip 文件格式。文件校验通过后直接使用；缺失或损坏时通过 HTTP 下载、校验并保存到同一目录。数据库和组装后的资源仍位于 `.fbui/gm/`。

FBUI 在现有 `0.0.0.0:8888` HTTP 服务上提供 Store ROM 启动接口：

```bash
curl -X POST http://DEVICE_IP:8888/api/store/assets/123:open
```

成功会立即返回 `202 Accepted` 和 `{"status":"accepted","asset_id":123}`。这只表示任务已经受理；资源下载、校验、ZIP 组装和模拟器启动会继续在设备端执行。接口只接受属于 Release 的 ROM asset，其他资源不会打开；同时只能执行一个远程打开任务。

接口允许 GM 管理页面跨域调用且没有鉴权，只应在可信局域网中启用。

## 实验：弹性 CPU 与降频

在 Linux 掌机上手动启用（需要 sysfs 写权限）：

每 3 秒 读取 `/proc/stat`：fbui 前台使用 CPU0，其他可热插拔核心下线；频率最低值降低至硬件最低值，最高值限制为「硬件最低值 + 启动时最高值与硬件最低值差值的 1/3」，实际频率交给 schedutil/ondemand。

游戏或其他外部程序运行时恢复启动时的频率上限，从 2 核开始；平均利用率达到 80% 或任一核心达到 90% 时，每次增加 1 核。扩核后至少等待 5 秒，随后持续低负载 10 秒才减少 1 核；收核要求剩余核心的预计负载低于 55%，且当前没有超过 70% 的忙核。外部程序刚启动时通常保留约 10 秒加载余量。CPU 热插拔前后的统计样本不用于负载决策。

这是**整机** CPU 热插拔及 CPUFreq 控制，会每轮重申设置，覆盖模拟器脚本中的核数、最低频率和 governor。通过日志中的“弹性 CPU”观察核数变化。任何读写失败都会停止控制并尝试恢复；正常退出 fbui 时也恢复启动前设置。强制杀进程、断电不能执行恢复，可重启设备恢复系统启动配置。暂未在真机验证帧率或节电效果；试用后退出并去掉环境变量即可关闭。

## 说明

目前这版是一个**默认关闭、每 3 秒检查一次的整机 CPU 控制器**，它直接控制核心上下线和频率范围。

**启动时**，先记录原来的核心在线状态、调频策略、最低频率和最高频率，供退出时恢复。然后寻找 `schedutil` 或 `ondemand` 调频策略；不支持就不开启实验。

**fbui 在前台时**，每轮都执行：

- 保留 CPU0，其他可控制的核心下线。
- 最低频率降到硬件支持的最低值。
- 最高频率限制为：`硬件最低频率 + (启动时最高频率 − 硬件最低频率) / 3`。
- 范围内的实际频率由系统自动调整。

例如，硬件最低 200 MHz、启动时最高 2 GHz，界面阶段最高就限制到 800 MHz。这里目前是固定限制，没有针对界面交互临时提频。

**游戏或外部程序运行时**，通过 fbui 的 `Detached()` 状态判断，恢复启动时的最高频率，并以 2 核作为起点。它没有识别具体游戏；把屏幕和输入交给其他程序，也算这个状态。

随后每 3 秒读取 `/proc/stat`，计算各在线核心在这段时间内的忙碌比例。满足任一条件就增加 1 核，直到全部开放：

- 所有在线核心的平均利用率 ≥ 80%。
- 任意一个核心的利用率 ≥ 90%。

因此，即使只有一个主线程很忙，也会触发扩核。**这只是启发式判断，扩核未必能解决单线程瓶颈。** 另外，进入游戏的第一轮也可能马上触发扩核，所以不保证一定先保持 2 核。

**收核比较保守**。扩核后先冷却至少 5 秒，再要求连续约 10 秒符合以下条件，才减少 1 核：

- 最忙的核心利用率低于 70%。
- 假设少一个核心，剩余核心的预计平均负载低于 55%。

第二条用的是这个估算：

```text
预计负载 = 当前平均利用率 × 当前核数 ÷ 减少后的核数
```

例如，2 核平均占用 20%，收成 1 核估计是 40%，可以进入收核等待；2 核平均占用 40%，收成 1 核估计是 80%，就不收。等待期间负载不再符合条件，会重新计时。游戏刚进入时设置了约 10 秒的收核冷却；如果触发扩核，则改用扩核后的 5 秒冷却。

还有几个实际行为需要说明：

- 核心上下线前后，跳过跨越变化的负载样本，避免累计计数造成误判。
- 每轮都会检查并纠正 sysfs 设置，值相同就不写；所以模拟器脚本改了核数、频率或调频策略，可能会被覆盖回来。
- 运行中读取统计或写设置失败，就停止控制并尝试恢复原设置；正常退出也会恢复，强杀和断电无法执行恢复。
- 当前只测了决策逻辑、模拟 sysfs 和构建，**还没有真机帧率、功耗数据**。

还有一点纠正之前的表述：这版并没有“先升频、再按需扩核”的分阶段控制。实际是**界面阶段固定限频，游戏阶段恢复原频率上限，再动态增减核数**。
